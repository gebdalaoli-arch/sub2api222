# Windows 桌面更新系统设计文档

- 日期：2026-04-18
- 状态：设计已确认，待进入实现计划
- 范围：Windows 桌面客户端更新流、服务端更新接口、管理后台桌面更新中心
- 关联项目：`desktop-client`、服务端 `desktop updates` 接口、后台发布页

## 背景

当前桌面客户端已经具备 Windows 安装包打包链路：

- 可通过 [build-desktop-installer.ps1](D:/挣钱/token/token客户端/build-desktop-installer.ps1) 生成安装包
- 可产出对应的 `SHA256` 校验文件
- 客户端内部尚未具备版本检查、下载更新、静默安装和重启能力
- 服务端也尚未提供桌面更新检查接口和管理后台发布入口

这次新增的是一套完整的 Windows 桌面更新系统，而不是单一的“更新弹窗”：

- 客户端负责检查更新、展示弹窗、下载、校验、安装与重启
- 服务端负责提供版本策略、安装包地址、更新说明和公告瀑布
- 管理后台负责上传安装包、管理版本、发布公告和控制强制升级

## 目标

- 首版仅支持 `Windows` 桌面客户端更新
- 更新源走自家服务器，不依赖第三方发布源
- 客户端启动时自动检查更新，并在设置页支持手动检查
- 默认允许可选升级，部分版本支持强制升级
- 客户端支持：
  - 发现新版本弹窗
  - 下载进度展示
  - 下载完成后 `立即更新 / 稍后`
  - `sha256` 校验
  - 静默安装
  - 安装完成后自动重启
- 后台支持：
  - 上传 Windows 安装包
  - 编辑更新说明
  - 管理公告瀑布
  - 发布 / 下线版本
  - 配置强制升级与最低支持版本

## 非目标

- 首版不支持 macOS、Linux 自更新
- 首版不做差分更新、增量补丁或二进制热更新
- 首版不做灰度百分比、发布通道或 Beta 通道
- 首版不做自动回滚
- 首版不做外部更新源聚合

## 已确认的产品决策

以下约束已在设计讨论中确认：

- 更新系统首版只做 `Windows`
- 更新源放在自家服务器
- 服务端使用独立更新接口，例如 `/desktop/updates/*`
- 管理后台提供单独页面管理桌面更新
- 客户端启动时自动检查更新
- 设置页支持手动检查更新
- 下载完成后弹窗提示 `立即更新 / 稍后`
- 强制更新时不能进入主界面
- 默认是可选升级，部分版本可以强制升级

## 推荐架构

推荐拆成 3 个清晰子系统：

1. 客户端更新流
2. 服务端桌面更新接口
3. 管理后台桌面更新中心

三者之间的关系如下：

- 管理后台维护“已发布的 Windows 版本记录”
- 服务端根据当前客户端版本计算“是否有更新、是否强制、显示什么内容”
- 客户端只消费服务端返回的结果，不自行推断升级策略

## 客户端更新流设计

### 1. 启动时检查

客户端启动后执行以下流程：

1. 进入正常开屏
2. 后台请求更新检查接口
3. 若无更新，不打断用户，进入主界面
4. 若存在可选更新，弹出更新弹窗
5. 若命中强制更新，直接进入强制更新态并拦住主界面

### 2. 设置页手动检查

设置页提供 `检查更新` 操作：

- 用户手动触发更新检查
- 若无更新，提示当前已是最新版本
- 若有更新，复用同一套更新弹窗

### 3. 更新弹窗

更新弹窗为全局系统态，不是普通设置页。

推荐内容结构：

- 标题：`发现新版本`
- 最新版本号
- 当前版本号
- 更新摘要
- 更新说明正文
- 公告瀑布内容
- 下载进度
- 操作按钮

### 4. 客户端更新状态

客户端至少支持以下状态：

- `checking`：检查中
- `available_optional`：发现可选更新
- `available_required`：发现强制更新
- `downloading`：下载中
- `download_failed`：下载失败
- `verifying`：校验中
- `verify_failed`：校验失败
- `ready_to_install`：下载并校验完成，等待安装确认
- `installing`：安装中
- `install_failed`：安装失败
- `completed`：更新完成，准备重启

### 5. 下载过程

客户端下载更新包到本地临时目录。

行为要求：

- 必须展示真实下载进度
- 可选更新允许取消下载
- 强制更新不允许跳过，只允许重试
- 下载完成后必须进行本地 `sha256` 校验

### 6. 安装与重启

当状态进入 `ready_to_install` 后：

- 用户可选 `立即更新`
- 或者 `稍后`

点击 `立即更新` 的客户端行为：

1. 写入必要的本地安装上下文
2. 安全退出当前客户端
3. 静默执行新的安装包
4. 安装完成后重新启动新版客户端

如果安装失败：

- 必须向用户展示正式错误信息
- 保留下载好的安装包路径
- 允许再次尝试安装

### 7. 强制更新拦截

当命中强制更新版本时：

- 不允许进入主界面
- 不允许关闭弹窗继续使用
- 只允许执行下载、重试、安装

这是首版强制更新的明确策略，不做“继续使用但持续提醒”。

## 服务端接口设计

推荐路由命名空间：

- `GET /desktop/updates/check`
- `GET /desktop/updates/releases/:id`
- `GET /desktop/updates/releases/:id/package`
- `GET /desktop/updates/announcements`
- 管理后台使用 `/admin/desktop/updates/*`

### 1. 检查更新接口

#### `GET /desktop/updates/check`

请求参数建议包含：

- `platform=windows`
- `arch=x64`
- `current_version=0.1.0`

返回结构建议包含：

- `has_update`
- `current_version`
- `latest_version`
- `release_id`
- `force_update`
- `title`
- `summary`
- `published_at`
- `sha256`
- `file_size`
- `download_url`
- `release_notes`
- `announcement_items`

行为规则：

- 若当前版本不是最新，返回可选更新或强制更新
- 若当前版本低于最低支持版本，`force_update=true`
- 若当前平台没有对应安装包，则 `has_update=false`

### 2. 版本详情接口

#### `GET /desktop/updates/releases/:id`

用途：

- 获取某个已发布桌面版本的完整详情
- 用于客户端在需要时拉取更完整的发布说明
- 也可供后台编辑后验证展示结果

### 3. 安装包下载接口

#### `GET /desktop/updates/releases/:id/package`

用途：

- 下载指定版本的 Windows 安装包

设计要求：

- 下载始终走自家服务器
- 客户端不直接依赖外部对象存储公开 URL
- 后续若要接 CDN、鉴权、下载统计，不需要改客户端协议

### 4. 公告接口

#### `GET /desktop/updates/announcements`

用途：

- 提供公告瀑布数据
- 可供更新弹窗和客户端公告中心共用

## 版本策略模型

服务端需要维护一套明确的版本判断规则。

推荐每条桌面版本记录至少包含：

- `id`
- `version`
- `platform`
- `arch`
- `title`
- `summary`
- `release_notes`
- `announcement_items`
- `package_path`
- `file_size`
- `sha256`
- `published_at`
- `is_published`
- `is_force_update`
- `minimum_supported_version`

其中关键语义如下：

- `is_force_update`：该版本是否对较旧客户端触发强制更新
- `minimum_supported_version`：低于这个版本的客户端直接被拦住
- `is_published`：仅已发布版本对客户端可见

## 管理后台设计

后台建议提供一个独立页面：`桌面更新中心`

### 1. 版本发布区

用于管理每个 Windows 桌面版本。

功能至少包括：

- 新建版本
- 编辑版本
- 上传安装包
- 替换安装包
- 发布 / 下线
- 查看历史版本

展示字段建议包括：

- 版本号
- 平台
- 文件大小
- `sha256`
- 发布时间
- 发布状态
- 是否强制更新
- 最低支持版本

### 2. 更新说明区

用于编辑客户端更新弹窗中看到的内容。

建议支持：

- 标题
- 摘要
- 正文
- 分组内容，例如：
  - `新增`
  - `修复`
  - `变更`
- 排序

### 3. 公告瀑布区

用于独立发布公告，不强依赖发版。

每条公告建议包含：

- 标题
- 正文
- 类型，例如：
  - `更新`
  - `维护`
  - `提醒`
  - `推荐`
- 是否置顶
- 生效时间
- 失效时间
- 是否与某个版本绑定

### 4. 发布流程

后台推荐发布流程如下：

1. 创建版本记录
2. 上传安装包
3. 自动计算或确认 `sha256`
4. 编辑更新说明
5. 配置是否强制升级
6. 配置最低支持版本
7. 选择是否同步公告瀑布
8. 点击发布

### 5. 管理后台保护规则

后台必须包含以下保护：

- 开启强制更新时必须二次确认
- 已发布安装包不允许无痕替换
- 如果替换包体，必须产生可追踪变更记录
- 已发布版本的 `sha256` 必须和下载包一致

## 数据安全与完整性

### 客户端侧

- 下载完成后必须进行 `sha256` 校验
- 校验失败不得执行安装
- 强制更新失败也不得绕过校验

### 服务端侧

- 安装包下载地址由服务端统一提供
- 客户端只信任服务端返回的版本记录
- 后台不允许生成“版本记录”和“包体内容”不一致的数据

## 错误处理

### 客户端错误

客户端需要明确区分：

- 检查失败
- 下载失败
- 校验失败
- 安装失败
- 重启失败

提示规则：

- 核心错误信息使用正式产品语言
- 可附带简短的人格文案，但不能替代真实错误
- 强制更新场景必须给出可重试路径

### 服务端错误

服务端需要明确区分：

- 当前版本已最新
- 当前平台无可用安装包
- 当前版本需要强制升级
- 指定 release 不存在
- 安装包下载失败

## UI 约束

更新页的视觉风格可以参考现有高质量桌面产品，但要统一到 `一键开整` 的产品语义中。

界面要求：

- 使用正式层文案作为标题、操作按钮和错误提示
- 电子牛马文案只出现在次级状态位
- 强制更新时去掉关闭与“稍后”
- 下载中、安装中、失败态要有清晰进度和动作反馈

## 首版验收标准

### 客户端

- 启动时会自动检查更新
- 设置页可手动检查更新
- 可选更新会弹出更新页，但不阻塞主界面
- 强制更新会阻塞主界面
- 下载过程显示真实进度
- 下载完成后会执行 `sha256` 校验
- 点击 `立即更新` 后会退出并静默安装
- 安装完成后能重启到新版客户端

### 服务端

- 能根据 `platform + arch + current_version` 返回正确更新策略
- 能区分可选升级与强制升级
- 能返回版本说明与公告数据
- 能提供安装包下载能力

### 管理后台

- 能创建和发布 Windows 更新版本
- 能上传安装包并记录 `sha256`
- 能编辑更新说明
- 能管理公告瀑布
- 能配置强制升级与最低支持版本

## 后续扩展方向

以下能力与本设计兼容，但明确不进入首版：

- macOS 更新
- Linux 更新
- 差分更新
- 灰度发布
- Beta / Stable 通道
- 自动回滚
- 版本下载统计与地区调度
